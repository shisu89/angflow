# Deletion via `getElementsToRemove` — Implementation Plan (sub-project C)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every way of deleting elements in angflow (keyboard, `NgFlowService.deleteElements`, Controls button, agent `delete_elements` tool, agent `apply_changes` → `delete_elements` op, plus `dissolveGroup`) behaves like upstream React Flow's `deleteElements`:
- deleting a parent deletes its descendants;
- `deletable: false` is respected for nodes and edges;
- connected edges are removed;
- `onBeforeDelete` can veto or narrow the set;
- the delete callbacks fire once, in upstream's order.

No version bumps. The work lands in the unreleased system 0.1.14 / angular 0.3.22 / mcp 0.0.4 entries.

**Architecture:**
- One implementation, `NgFlowService.deleteElements`, mirrors upstream `useReactFlow().deleteElements` (`packages/react/src/hooks/useReactFlow.ts` on `upstream/main`). It calls system `getElementsToRemove`.
- The keyboard (upstream `useGlobalKeyHandler`), the Controls button and the agent `delete_elements` tool all call it.
- The `apply_changes` op keeps its snapshot-rollback batch. It awaits `getElementsToRemove` with no hook.
- `dissolveGroup` reparents the children first, then deletes the group, and restores the children if the group wasn't deleted.
- The system function first gets the two upstream changes angflow is missing (#6074, #6111; Spec deviation 1).

## Spec deviations

The spec stays the contract. In the places below, the code differs from what the spec says, and the plan follows the code as described.

1. **`getElementsToRemove` is *not* byte-identical to `upstream/main`.**
   - `git diff upstream/main -- packages/system/src/utils/graph.ts` shows that angflow still has the pre-#6074 array scan. It has neither #6074 (merge `867023dd8`, Map lookups) nor #6111 (merge `910eb791e`, commit `5161767ec`, which removes descendants regardless of node order).
   - Without #6111, a child listed before its parent isn't cascaded. The spec's own test ("cascade (3 levels, child listed before parent)") would fail.
   - The report always scheduled them for C (§5 row C: "+ #6074/#6111").
   - **Task 1 ports both.** Checked in a temporary index: #6074's `graph.ts` hunk applies cleanly to BASE, and #6111's applies cleanly on top of it.
   - #6111 adds `graph.test.ts`, but angflow's system vitest only includes `src/**/*.spec.ts`. Its cases go into `graph.spec.ts`.
   - The semantics the spec lists (skip `deletable: false` before the cascade, protected subtrees survive, store order, verbatim object result) are exactly the post-#6111 function's.
2. **Task order keeps every commit green.** Once `deleteElements` cascades, today's `dissolveGroup` (delete first, then reparent) would delete the children. So `dissolveGroup`'s reparent → delete → restore lands first (Task 2). It works against today's non-cascading `deleteElements` too. The two `dissolveGroup` cases that need the new semantics (a narrowing hook, a `deletable: false` group) are added in Task 3.
3. **The `delete_elements` *tool* description, its `AGENT_BRIDGE.md` row and the mcp snapshot move into Task 3.** That commit changes the tool's behaviour (cascade, `deletable`), and the same-commit rule applies. Task 6 does the `apply_changes` op and its own docs/description/snapshot.
4. **`dissolveGroup` position arithmetic.**
   - The spec's `childAbs − newParentAbs` is exact only at `nodeOrigin [0,0]` for an unclamped child.
   - The plan uses `internals.positionAbsolute`, which is what's drawn, including any `extent: 'parent'` clamp. It adds the child's `dims × origin`, the inverse of how the system derives `positionAbsolute`.
   - At origin `[0,0]` this reduces to the spec's formula.
   - Restore and the returned ids skip children that no longer exist. The spec leaves this unstated. An `onBeforeDelete` object result is used verbatim, so it could delete a child.
5. **`apply_changes` can't keep a delete op inside `flow.batch()`.**
   - `FlowStore.batch(fn)` is synchronous: it only coalesces `version` bumps while `fn` runs. An `await` inside it would end the batch early.
   - Revised in review:
     - `executeOp` stays synchronous for every op except `delete_elements`;
     - runs of non-delete ops stay in one synchronous `flow.batch()`, exactly as today;
     - a `delete_elements` op closes the run, awaits `getElementsToRemove` (no hook, so microtasks only) and batches its own writes.
   - A batch without a delete op is unchanged and fully synchronous.
   - Nothing renders, and no `flow.state` goes out, between ops in either case:
     - zoneless change detection and the zonal `onMicrotaskEmpty` both wait for the microtask queue to drain;
     - the bridge's `flow.state` emission runs from an effect.
   - The "single reactivity cycle" contract and its existing test still hold. `AGENT_BRIDGE.md`'s rollback point 2 is reworded.
6. **Existing tests that encode the old behaviour change in the fixing commit:**
   - `key-handler.directive.spec.ts`: all three `TestBed` setups provide only `FlowStore`, so they gain `NgFlowService`. The two `'Meta+Backspace'` delete tests subscribe to the removed `directive.nodesDelete` output, so they assert on the store after a flush instead (Task 4).
   - `controls.component.spec.ts` `'excludes elements with deletable === false'` asserts `deleteElements` is *not* called. It becomes a real-service test asserting the locked node survives (Task 5).
   - `agent-bridge.spec.ts` `'delete_elements cascades edges of deleted nodes'` stays green unchanged.

## Open questions

Each has a default, and the plan implements the default. Answer before the named task if you want the alternative.

1. **`onBeforeDelete` with an empty matched set (Task 3).**
   - Upstream's `getElementsToRemove` calls the hook even when nothing matched, for example Delete with only `deletable: false` elements selected, or `deleteElements({ nodes: [{ id: 'ghost' }] })`. A confirm-dialog hook would then pop up for nothing.
   - Today's angflow service skips the hook when the set is empty. The spec says "Empty input or nothing matching: no callbacks, no changes".
   - **Default:** pass `getElementsToRemove` a wrapper that returns `true` without calling the host hook when the matched set is empty.
   - **Alternative:** upstream-exact (the hook sees `{ nodes: [], edges: [] }`).
2. **Keyboard delete with nothing selected (Task 4).**
   - **Default:** upstream-exact. No early return: call `deleteElements` with the (possibly empty) selection and clear `nodesSelectionActive` on every delete press. With Open question 1's default, an empty press calls no hook and no callback.
   - **Alternative:** keep today's early return.
3. **Controls `deleteClick` when nothing was deleted (Task 5).**
   - Today it emits `{ nodes: [], edges: [] }` after a veto, and doesn't emit at all when the selection is all `deletable: false`, because the pre-filter returns early.
   - **Default:** keep the "nothing selected" guard (the button is disabled then anyway). Emit `deleteClick` with whatever `deleteElements` returned, possibly empty.
   - **Alternative:** emit only when something was deleted.
4. **In-process `callTool` calls made concurrently with an `apply_changes` that contains a delete op (Task 6).**
   - Transports deliver each request in its own macrotask, so they can't interleave.
   - A host that calls `bridge.callTool('apply_changes', …)` with a delete op and `bridge.callTool('add_node', …)` in the *same tick*, without awaiting, can now have `add_node` run at the delete's microtask boundary. A later rollback would then erase it.
   - Batches without a delete op are unaffected; they stay synchronous.
   - **Decision (review):** document it in `AGENT_BRIDGE.md` ("await `apply_changes` before issuing another in-process call"). No mutex or queue.

### Task 2 (opus): `dissolveGroup` reparents, then deletes, then restores on veto

This task lands before the cascading `deleteElements`, so every commit stays green. Once deletion cascades, the old delete-then-reparent order would delete the children. The new order works with today's `deleteElements` too: no cascade, a boolean hook, and it removes the group and its connected edges.

Restated decisions this task relies on:
- **Position (Spec deviation 4).** A child keeps the position it's drawn at (`internals.positionAbsolute`, which includes any `extent: 'parent'` clamp). It's converted to a raw position under the new parent with `relative = abs − parentAbs + dims·origin`. At origin `[0,0]`, for an unclamped child, that equals the spec's `childAbs − newParentAbs`.
- **Restore and return** skip children that no longer exist. An `onBeforeDelete` object result is used verbatim, so it could delete a child.
- **A child that overhangs the grandparent.** An `extent: 'parent'` child moved under a grandparent keeps `extent: 'parent'`. If it overhangs the grandparent, the store's extent clamp pulls its *drawn* position into the grandparent, while its raw `position` is what was written. This matches what today's code ends up with (spec: "the grandparent's clamp applies, as it would today"), and it's accepted. Task 7 documents it in the changelog.

### Task 6 (opus): `apply_changes` → `delete_elements` op uses `getElementsToRemove` (async only for delete ops)

Restated decisions this task relies on:
- **`onBeforeDelete` is still bypassed** inside `apply_changes`, with the existing one-time warning (spec non-goal).
- **Only `delete_elements` goes async (Spec deviation 5, as revised in review).**
  - `executeOp` stays synchronous for every other op. Consecutive non-delete ops still run inside one synchronous `flow.batch()`, exactly as today.
  - A `delete_elements` op ends the current batch, awaits `getElementsToRemove` (no hook, so only microtasks), applies its removals in its own `flow.batch()`, and the next ops start a new batch.
  - A batch with no delete op is fully synchronous: no `await` runs, and the store is updated before `callTool`/`dispatch` returns its promise.
  - `FlowStore.batch(fn)` is synchronous; it only coalesces `version` bumps. Never pass it an async function.
- **In-process interleaving (Open question 4 default).**
  - This applies only to batches that contain a delete op.
  - Another in-process `callTool` started in the same tick can run at that delete's microtask boundary, and a later rollback would undo it.
  - Transports can't do this, because each request arrives in its own macrotask.
  - Document it in `AGENT_BRIDGE.md`. **No mutex or queue.**

**Call chain, checked at BASE:**
- A transport (or `callTool`) calls `dispatch(req)`, which is async.
- `dispatch` runs the `canMutate` await, if set, and takes the history `snapshot` for `MUTATING_TOOLS`/`apply_changes`. Then it runs `const result = await handler(flow, params)`.
- `dispatch` then does the op-log/history recording.
- Its `catch` maps `InvalidParamsError` to `-32602`, and `ApplyChangesError` to `-32603` with `data.failedIndex`.

The `apply_changes` handler (`this.handlers.set('apply_changes', …)`, ~:946) does these steps in order:
1. the `requestedElements` aggregate pre-check, which throws `InvalidParamsError`;
2. the one-time `onBeforeDelete` bypass warning;
3. the rollback `snapshot`;
4. `flow.batch(() => { for … results.push({ ok: true, value: executeOp(flow, ops[i]) }) })`;
5. on failure, the batch restore and a `throw new ApplyChangesError(...)`.

`executeOp` (module-level function, ~:1288) is only called from that loop. `ToolHandler` already allows `Promise<unknown>`.

Making the handler `async` keeps every error path. An `async` function body runs synchronously until its first `await`, so a batch with no delete op still completes inside the call. A synchronous `throw` inside an `async` handler becomes a rejection, and `dispatch`'s `await handler(...)` catches it in the same `try`. So the pre-check still returns `-32602` before any mutation, and `ApplyChangesError` still returns `-32603` + `failedIndex`.
